# 文件输入与多文件审核

涉及文件上传、文档解析、图纸图片、多文件内容传递或一致性审核时读取本文件。通用原理参考 FastGPT 官方文档；字段结构以目标 FastGPT 兼容实例保存后的真实回导为准。

## 1. 文件链路由三层组成

不要把“系统配置里已开启文件上传”等同于工作流已可用。至少回读以下三层：

1. 应用级上传配置：目标实例当前回导位于 `chatConfig.fileSelectConfig`。
2. 开始节点输出：`workflowStart` 必须包含 `userFiles`，类型为 `arrayString`。
3. 下游引用：判断、AI、文档解析、插件或子工作流必须显式引用开始节点的 `userFiles`。

某次 FastGPT v481 节点结构的真实回导片段如下。它是结构证据，不是所有项目都应照搬的业务参数：

```json
{
  "chatConfig": {
    "fileSelectConfig": {
      "maxFiles": 10,
      "canSelectFile": true,
      "canSelectImg": false,
      "canSelectVideo": false,
      "canSelectAudio": false,
      "canSelectCustomFileExtension": true,
      "customFileExtensionList": [],
      "customPdfParse": true
    }
  }
}
```

同一回导中，系统配置节点 `userGuide.inputs` 仍可能为空；因此不要把上传配置写进该节点并假定平台会识别。目标实例保存后新增的开始节点输出形态为：

```json
{
  "id": "userFiles",
  "key": "userFiles",
  "label": "app:workflow.user_file_input",
  "description": "app:workflow.user_file_input_desc",
  "type": "static",
  "valueType": "arrayString"
}
```

判断节点常用引用：

```json
{
  "variable": ["workflowStartNodeId", "userFiles"],
  "condition": "isNotEmpty",
  "valueType": "input"
}
```

AI 节点的文件链接输入通常是引用数组：

```json
{
  "key": "fileUrlList",
  "valueType": "arrayString",
  "value": [["workflowStartNodeId", "userFiles"]]
}
```

如果导入时上游尚未产生 `userFiles`，平台可能把下游引用显示为“选择引用变量”并在保存时丢弃。正确恢复顺序是：开启上传并保存 → 确认开始节点出现 `userFiles` → 重绑判断/解析节点 → 再保存和回导。

## 2. 文档与多模态必须分开判断

- PDF、Word、Excel、Markdown、HTML 等普通文档通常先转成文本，再拼接到提示词；模型并不是直接理解原文件格式。
- 图片、音频、视频不会由普通文档解析节点处理，需要启用相应上传类型并绑定支持该模态的模型或 OCR 工具。
- `aiChatVision=true` 只表示节点允许视觉输入，不证明当前模型真正支持图片。
- 自定义扩展名只控制“允许选择/上传”，不证明解析器支持该格式。例如业务中存在 `.xls` 或 `.xlsm` 时，应先做目标实例运行测试；没有证据时优先转为 `.xlsx`。
- 工作流调用插件或子工作流时，不假定文件会自动透传；逐个绑定文件 URL 输入。

## 3. 多文件审核的完整性门禁

多文件分析不能只校验最终答案是否非空。至少记录：

- 本轮上传文件数；
- 已生成文档台账数；
- 每个文件名、识别类型、版本、已读取工作表/页码和解析告警；
- 结构化记录数及低置信记录数；
- 未识别、加密、空表、扫描件、截断或超过上下文的文件。

上传文件数大于已生成文档台账数时，应阻止“审核完整/可以放行”结论。文件级数量一致仍不能证明逐行完整；大工作簿和长 PDF 应增加工作表、页数、关键段落或记录数的抽样回读。单模型节点同时接收大量文件时，优先拆为逐文件解析、汇总台账、确定性比对三个阶段。

## 4. 一致性不等于准确性

多个文件值相同只能证明“一致”，不能证明严重度、符号、阈值或措施本身正确。用户要求“准确”时，必须明确权威依据，例如：

- 已批准的特殊特性判定/符号基准表；
- 客户特殊要求或企业标准；
- 权威文件优先级和版本；
- 严重度、特殊特性类别与符号映射；
- 特性编号、工序编号和适用范围。

没有权威依据时，在报告中写明“仅完成跨文件一致性审核”，不要根据模型常识推导正确值。

## 5. 传递链审核设计

先把每份文件抽取为统一台账，保留 `document_type`、`source_name`、`locator`、原文证据、特性/失效/工序标识、严重度、特殊类别、符号、规格、措施、参数、频次和反应计划。再用确定性规则执行：

1. DFMEA → 产品特殊特性清单 → 图纸；
2. DFMEA → PFMEA；
3. 产品特殊特性 → 过程特殊特性；
4. 过程流程图 → PFMEA → 过程特殊特性 → 控制计划 → 作业指导书。

第四条链不能只检查工序名称是否出现。还要覆盖严重度、特殊特性及符号、预防措施、探测措施、控制方法、参数/参数值、频次和反应计划。候选匹配可用文本相似度，但特性编号、工序号和工站号存在时必须优先精确匹配；语义相反的失效模式不得因词面接近而合并。

## 6. 回导与回归

候选 JSON 导入后：

1. 保存并重新导出；
2. 比较节点 ID、类型、边四元组、模型、布局和输入键；
3. 特别检查 `fileSelectConfig`、`userFiles` 和所有文件引用；
4. 用文档、图片、空文件、加密文件、超大文件、混合版本和部分缺失文件运行回归；
5. 分享页需要重新打开，确认附件入口真实出现；
6. 接口调用场景单独验证文件 URL 传递，不以网页上传成功替代接口证据。

目标平台自动增加 AI 节点输入键时，记录为版本漂移并把回导文件升级为新基线；不要删掉未知键以强行恢复旧模板。

## 7. 可复用脚本

`scripts/configure_file_input.py` 用于对现有 JSON 做最小、可审计的文件输入补丁。它可以写入应用级配置、补齐开始节点 `userFiles`，并按显式节点 ID 重绑判断和 AI 文件输入。脚本只生成候选文件；仍需在目标实例导入、保存、回导和运行验证。
