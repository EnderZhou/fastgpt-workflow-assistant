# 专家实测与证据交付

处理普通用户多轮任务、测试反馈、版本询问及交接时读取。依据2026-11普通用户试用中的版本漏检、断言误命名和兼容性过度结论整理；不带入案例的具体IP规则、单目标限制、节点数量或平台地址。

## 查证版本与实际生效状态

不要只列非隐藏文件或只读 Agent frontmatter。WorkBuddy 专家查看包根 `.codebuddy-plugin/plugin.json` 的 version；内置技能查看 `skills/<name>/assets/skill-version.json` 和 SKILL.md。版本来源缺失时记“未知”，不下“不存在”的结论。`.downloaded_at` 只作下载时间线索，不能当审核通过或最新版证据。

使用 `scripts/inspect_expert_versions.py <专家目录或ZIP>` 只读盘点专家与内置技能版本、相互引用和SHA256；它不会联网，也不能判断市场是否已生效。单独技能也可盘点。

分别报告专家包、内置技能、目标FastGPT平台、节点格式和应用标签。节点version=481不代表服务器版本。源码tag审查只证明已核对的代码点，不能推断所有版本导入成功或“唯一写法”。

本项目从3.0.0起按维护者要求将专家和技能发行号对齐，但保留独立字段，逐包核对相等。机器名 `fastgpt-workflow-expert` / `fastgpt-workflow-assistant` 不变。2.x技能安装及工作流格式不因本次对齐而强制迁移。平台上架版本、审核中候选、本地候选、GitHub Release分别记，不用新包覆盖“线上版本”的事实。

## 证据要对应结论

- 读JSON/检查语法/结构图可达性、函数调用、条件与连线路由仿真、平台导入回读、真实运行是不同层；按实际执行记录，不能把通过条数作为证明。
- “普通查询不会执行检测”须验证正确分支与完整连线上的动作节点，而不只是某个target字段有值。断言名称准确描述实际比较；一个场景可能有多条断言，不把40条断言叫40个独立场景。
- 主要检查交付JSON内嵌代码与真实edges。只测试src时先比较它与交付JSON中的代码是否一致，否则没有证明交付物。不要在测试中手工返回预期intent来代替输入解析验证。
- 路由条件仿真注明支持的操作符、引用、AND/OR及未知语义。遇到未知条件、节点或循环状态应标记未覆盖/拒绝判定，不能默认false或跳过后给通过。平台语义以目标版本源码与实际回读为依据。
- 图检查沿每个选中分支的**全部**出边检查潜在动作；不能发现常规边后忽略额外出边，也不能只沿第一条边掩盖误连。回复节点的异常出边需报出。条件、句柄、引用、节点及四元组一致性都应可审查。
- 当路由保证是核心验收时，用少量有代表性的变异确认检查器会失败，例如误接动作边、增加旁路动作、删除兜底、修改条件。检查应通过明确断言失败拦截，不把脚本崩溃或缺环境当成功抓错。不为简单文字修改搭建庞大的测试工程。
- 离线模拟“接口就绪”时只在内存或独立副本中改变开关，记录与原包差异。没有请求记录不等于证明全程零网络；清楚区分“按要求未调用接口”“代码未包含网络动作”和“经过网络监控验证”。

可用 `scripts/check_route_contract.py <workflow.json> <contract.json>` 做**静态分支图契约**检查：从指定sourceHandle遍历所有后继边，检查必经/禁止节点、悬空边、缺失出口、终端出边与闭环。它不求值条件、不执行代码、不发HTTP，必须与输入判定验证和平台实测分开。契约示例为 `assets/route-contract.example.json`，节点/句柄必须替换为实际导出。

## 面对反馈与需求范围

先确认反馈是否有文件或运行证据；成立则更正结论和对应文档。用户说“不改JSON，只修记录”时保持工作流字节与哈希；构建脚本只改注释也应说明未重建。没有必要反复补测或不断增加检查数量。

短句沿当前任务承接：不加知识库、不改规则、先给方案等意图不得丢失。额外的单目标、仅内网、地址段限制、确认步骤或API总开关应依据项目契约；不能把旧案例策略固化为所有工作流默认。需要离线待配置门禁时按实际项目选择合适方式。

遇到导入未连线等问题，保留候选与回导，先检查edges四元组、条件、branchId/句柄映射和字段类型变化；它们是排查候选，不排名“最可能”除非有证据。更不能把断线直接归结版本差异，也不能让用户重连后就宣称生成正确。

## 面向普通用户的简短交接

默认先给结果、实际文件路径、必要配置和待验证事项。简短边界问题直接答，不自动展开源码函数、沙箱环境变量或源码tag。用户需要时再展开技术报告。

交接按顺序：先保留接口未启用态，在测试应用导入；确认图和实际代码沙箱；保存并回导比较；用无副作用用例验证；按真实契约填接口和凭据，最后启用动作。明确哪些步骤是导入前、哪些必须导入后，不能让用户在“导入前”执行平台对话。

没有证据不要断言“代码节点一定全报错”或“内网接口一定被拦”；写成待确认的环境依赖，依据实际报错处理。收集最小可用信息：报错原文、相关节点、平台版本（可得时）、回导JSON、输入/期望/实际、发生时间；HTTP信息仅在相关时收集并脱敏。缺一项先从已有证据排查，避免“缺一不可”“只能猜”。

最终答复中不要同时写“可直接用”与“平台未验证”造成验收错觉。用“候选JSON，离线检查通过；待目标实例导入/运行验证”，并指向当前唯一文件与完整报告。
