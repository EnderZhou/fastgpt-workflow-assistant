# 企业微信回复排版

适用于欢迎语、功能介绍、问答、操作指引、任务进度、异常和结果反馈。以目标实例和实际企微发布通道的渲染结果为依据，不假定所有客户端或消息类型都支持相同 Markdown/HTML。

## 展示规则

- 欢迎语/功能清单按实际业务分为2至4组，用短标题、空行和逐行项目符号；避免所有功能和使用提示挤成一个段落。普通换行与简短文本标签可作为兼容基础，不依赖大字号标题、颜色、嵌套HTML或复杂表格。
- 先给结论，再给必要信息和下一步。长的任务进度、异常解释和操作指引按语义分行；简短的一句话不必强加标题或列表。
- 并列功能用项目符号；有顺序的操作用编号；字段和值保持同一行，多个字段逐行展示。不要以空格模拟对齐。
- 沿用目标通道已验证的窄表格：单目标一般2列，批量一般3列；表头、表格前后留完整换行。单元格换行仅使用该通道已验证的形式（某些实例为受控 br）；字段值先转义，不能由不可信数据插入额外列、行或HTML。未验证支持时使用标签列表并说明实测边界。
- 任务编号、IP、MAC、链接、确认口令和示例命令完整保留，不能为排版插入空格/换行或改写。长链接不要凭视觉宽度裁剪，下载功能取消后不再展示旧链接。
- 机器人简介、欢迎语和业务结果是不同用途，分别遵循用户要求的长度限制；不能把简介的字数限制推广成所有回复的统一截断。

## 修改范围与实施

1. 检查当前提供/确认的所有相关工作流，不只修改被截图指出的欢迎语。枚举最终 answer/reply/text 字段、固定回复节点、最终自然语言AI节点和上游传回的展示文本。
2. 固定欢迎语直接整理成分组文本；已有清晰表格和简短回复保留。对长动态段落，可在最终展示字段增加确定性的格式化函数；不能全局替换JSON、原始正文或所有字符串。
3. 只在生成用户自然语言的模型提示词中添加展示规范。分类、OCR、结构化资料提取、代码/JSON输出不得混入面向读者的列表格式指令。
4. 展示适配不改变工作流业务拓扑、URL/鉴权、权限、确认条件、整批payload、状态机、幂等键和通知规则。需要包裹旧函数时保留原函数体，只格式化显式列出的用户可见输出字段；序列化 state、任务游标和工具请求体保持原样。
5. 不对Markdown表格行、代码围栏、变量模板、链接及引号内命令做机械标点拆分。换行不是业务截断，不能丢掉清单或隐藏接口失败。

## 验证

至少验证：欢迎语分组、正确助手身份、长进度和异常的可读性、单/批量表格与单元格换行不变、短回复不膨胀、命令与链接未变、提取JSON提示词未被污染；有写入能力的助手还要比较完整批次、确认口令、执行锁、保存状态和HTTP配置不变。

离线字符串/结构检查不能宣称手机企微已渲染通过。交付可导入候选或针对当前节点的精确补丁，并明确需要目标通道回读/展示验证。

可复用示例：`assets/code-snippets/wecom-reply-format.js`。仅作用于明确的最终展示字段；不得处理整个请求对象或持久化状态。
