# 企业 RAG 知识库工程

仅当工作流需要依据受控文档检索事实时使用本参考。纯 API 查询、确定性流程、写入审批、事件/批量或无需检索的模型任务不得为了套用平台能力而创建空知识库。

## 1. 以用户决策划分知识域

按“用户要做什么决定”划分，不按原始文件夹或产品名简单合并。典型知识域：制度与申请、平台操作、技术排障、产品手册、事件响应、固定诊断 SOP。

为每个知识域记录：允许意图、权威来源、责任人、更新周期、有效日期、淘汰规则、允许引用方式和安全等级。实时状态不得由静态知识覆盖。

## 2. 导入文档模板

```markdown
# 用户主题与常见说法

## 适用范围
说明适用与不适用情形。

## 结论
用一个短段落给出主要判断。

## 操作步骤
1. ...
2. ...
3. ...

## 结果判断
- 条件 A → 结论 A
- 条件 B → 结论 B

## 升级处理
说明需要收集的证据和责任渠道。

## 来源与版本
责任人、生效日期、来源名称、稳定官方 URL 或菜单路径。
```

每个检索单元语义完整；必须随答案出现的安全条件要写入每个相关主题，不依赖远处切片。标题和开头包含用户常用词、缩写、同义词和历史叫法。

## 3. 版本与重复治理

- 一个主题只保留一个当前索引版本。
- 原始 DOCX/PDF 与精简 Markdown 不同时入库，除非评测证明各有独特价值。
- 更新时备份旧文件、替换同名文档、重建索引并验证版本特定事实。
- 文件中记录内容版本，不把临时签名 URL 当作知识。
- 用 `scripts/audit_fastgpt_kb.py` 检查重复正文、重名文件、长度、标题、占位词、签名 URL 和原始引用标记。

### 3.1 版本化更新包目录

项目使用知识库且需要交付更新包时，默认按目标应用版本建立独立目录，避免新版文件直接覆盖上一版本。已有制品库或内容版本系统时，遵循项目规范并在发布清单中记录对应版本。推荐目录：

```text
{agent_name}_V{version}_知识库更新包/
└── FastGPT导入版/
    └── {知识库名称}/
        ├── 01_主题A.md
        ├── 02_主题B.md
        └── ...
```

示例：`示例应用_V1.2.0_知识库更新包/FastGPT导入版/流程知识库/`

要求：

- 仅在知识库内容发生变化时创建更新包；包含该版本涉及的全量或增量文件，并明确类型。
- 目录名必须含应用名称、版本号和“知识库更新包”后缀。
- 导入版子目录名固定为 `FastGPT导入版`，其下按知识库名称归集文件。
- 发版说明中记录本次更新包目录、文件清单和 SHA-256 哈希；公开材料不写本地绝对路径。
- 旧版本按项目保留策略保存，至少覆盖约定的回滚窗口；不要在 Skill 中强制永久保留。

## 4. 检索调优顺序

1. 修正文档结构、重复和过期内容。
2. 用真实用户改写测试原始召回。
3. 调整语义/全文/混合模式和相似度阈值。
4. 调整引用数量或 Token 上限。
5. 只有多轮指代或查询扩展失败时才增加问题优化。
6. 只有扩大召回后排序仍差时才增加重排。
7. 每次变更重测召回、错误命中、答案质量和延迟。

不要通过无限增大引用上限补偿文档质量。记录每个参数实验的前后指标和回滚值。

## 5. 评测集

每个重要主题至少包含：原句、口语改写、缩写、错别字/轻微噪声、相邻主题负例、无答案、过期版本问题。记录期望知识域、允许文档、禁止文档、关键事实、禁止内容和最大延迟。

## 6. 引用与输出安全

- 由平台真实元数据或检索记录生成来源，不让模型凭记忆编写来源清单。
- 明确禁止原始 chunk ID、collection ID、`CITE`、半截 Markdown 链接和临时签名参数。
- 敏感标识、内部地址和受限信息只在授权渠道、确有必要且来源受控时输出；对外样例使用占位符。
- 无稳定 URL 时返回完整菜单路径，不猜测地址。
